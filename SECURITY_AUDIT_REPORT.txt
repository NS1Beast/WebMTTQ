--------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------
This project is a Vietnamese "MTTQ neighbourhood committee" public
website plus an authenticated admin CMS. The codebase already contains
several good security practices: PBKDF2 password hashing, EF Core
parameterized queries, session-only authZ with a role-version
revalidation mechanism, generic production error handler, and HSTS.

The overall posture is "moderately hardened but inconsistently applied".
The main weaknesses are: (1) an admin content/graph module that only
requires login and not any module permission, (2) SMTP credentials
(and reset OTP values) stored or handled in plaintext, (3) a large
number of admin state-changing endpoints that lack an anti-forgery
token, (4) no server-side HTML sanitisation on admin-authored rich
content that is emitted with @Html.Raw, (5) no rate limiting or account
lockout on login / OTP, (6) client-supplied filename/type controls on
several uploads that land in a statically-served folder, (7) no
security headers beyond HSTS, and (8) several session/TLS hardening
gaps.

No confirmed CRITICAL (RCE / full-DB / admin-takeover) vulnerability
was proven from the static review alone. The most serious, realistic
risks are the missing-authorization admin modules and the plaintext
storage of SMTP credentials.

--------------------------------------------------------------------
2. PROJECT SECURITY OVERVIEW
--------------------------------------------------------------------
Authentication        : Custom session-based (not ASP.NET Identity)
                        - PBKDF2-HMAC-SHA256 (100000 iters) passwords.
                        - No plaintext passwords stored or compared.
                        - No OAuth / external SSO.
Authorization          : Attribute [KiemTraQu*y] (module/action) +
                        BaseAdminController login check. Roles stored in
                        DB, permissions cached in session with a DB
                        version for revalidation.
CSRF                   : Opt-in attribute [ValidateAntiForgeryToken].
                        NOT default-on; many POST sinks omit it.
SQL Injection          : Not found - all queries are EF LINQ/parameter.
XSS                    : HTML auto-escaped by the engine; @Html.Raw used
                        only for admin-authored rich content.
File uploads           : stored under wwwroot/uploads and served as
                        static assets; several endpoints lack a strict
                        extension allow-list.
CSP/Headers            : No CSP, X-Content-Type-Options,
                        X-Frame-Options, Referrer-Policy, or
                        Permissions-Policy configured.
HTTPS/TLS              : HSTS enabled (non-dev) and HTTP->HTTPS
                        redirect. SQL conn string has
                        TrustServerCertificate=True.
Rate limiting           : None for login/OTP/password reset; public
                        feedback/help forms have a 30-second session/IP
                        throttle.

5. HIGH VULNERABILITIES

---
## [HIGH] Missing module authorization (Broken Access Control)
Location:
Controllers/AdminGioiThieuController.cs (whole controller)
Controllers/AdminDoanTheToChucController.cs (whole controller)

Description:
Both controllers derive from BaseAdminController (login check only) and
declare a [Route] but DO NOT declare the [KiemTraQu*y] attribute, and
they do not perform any per-module permission check in their actions.
Every other admin controller gates Create/Update/Delete behind a module
permission (e.g. TrangChu, ThongTinUngHo, ...). These two do not.

Application scenario:
  A user with only the weakest role / no module permission logs in
  (any authenticated CMS account). They call
  /admin/gioithieu (or /admin/doanthe) directly and can Create, Edit
  and Delete organisation history / org-chart content without any
  module permission. The UI may hide the buttons, but the endpoint
  itself is open to any logged-in user.

Impact:
  Unprivileged authenticated user modifies/deletes content intended to
  be limited to specific roles -> data integrity loss, minor
  privilege escalation, unauthorised content management.

Evidence:
  - AdminGioiThiController class has only [Route("admin/gioithieu")]
    + " : BaseAdminController" (no [KiemTraQuy...]).
  - AdminDoanTheToChucController likewise only [Route("admin/doanhhe")]
    + BaseAdminController.

Recommended fix:
  Add [KiemTraQu*] attribute (e.g. TrangChu or a dedicated module) at
  class level, and add [ValidateAntiForgeryToken] to all POST actions.

## [HIGH] SMTP / sensitive settings stored in plaintext at rest
Location:
        Services/SystemSettingsService.cs (line 19: _encryptedKeys empty;
        lines 58-96 encrypt-aware getters fall back to plaintext)
        Controllers/AdminCauHinhController.cs (line 135: saves SmtpPassword
        via SetValueAsync - plaintext)
        Models/CauHinhHeThong.cs (GiaTriCauhinh is the raw value column)

Description:
  SystemSettingsService maintains a dedicated IDataProtector, but the
  list of "keys to encrypt" (_encryptedKeys) is initialised EMPTY and
  is never populated. The system settings POST controller saves the
  SMTP password using SetValueAsync (plaintext), not SetEncryptedValue.
  GetEncryptedValueAsync tries Unprotect(), fails, and on the catch
  "backward compatibility" path returns the value unchanged - i.e. the
  plaintext. The SMTP username/password therefore live in the DB in
  clear text.

Impact:
  Credential disclosure at rest. If the database (or a backup, or the
  admin CauHinh page) is read, the SMTP password - which can often be
  reused / be the mailbox password - is exposed. It also weakens the
  whole assumption of data protection for other sensitive settings.

Evidence:
  Services/SystemSettingsService.cs:
     private static readonly List<string> _encryptedKeys = new();
  Controllers/AdminCauHinhController.cs (~line 156):
     await _settings.SetValueAsync("SmtpPassword", model.SmtpPassword, "SMTP Password");
  Note: the "GET" of the same page also returns SmtpPassword (the
  decrypted/plaintext value) into the form model, so the secret is
  echoed into a served page (admin-scope).

Recommended fix:
  Move SmtpPassword to SetEncryptedAsync endpoints, seed the encrypted
  keys allow-list, and never echo the secret back unencrypted.
## [MEDIUM] CSRF - many admin POST actions missing anti-forgery
Location: AdminBannerController (Delete,ToggleStatus);
AdminTimelineController (ItemDelete,ItemToggle,UpdateSort);
AdminKetQuaChamLoController (Delete); AdminSoDuQuyController (Delete);
AdminDoanTheToChucController (Delete); several others.
Detail: anti-forgery is opt-in via ValidateAntiForgeryToken; many state-
changing POST handlers omit it. If a global CSRF filter is not enabled
by your framework version, these are exploitable via CSRF (a malicious
page/email triggers an admin browser to delete/toggle records). Verify
the framework default. MEDIUM.
Fix: add ValidateAntiForgeryToken to all mutating POSTs.
##
MEDIUM - Stored XSS via admin-authored rich HTML (no sanitizer)
Sinks: Views/Home/Index.cshtml @Html.Raw(sec.NoiDung);
Views/About/Index.cshtml @Html.Raw(sec.NoiDung);
Views/News/Details.cshtml @Html.Raw(Model.Content);
Views/CongThongTinAnSXH/*.cshtml @Html.Raw(ViewBag.MapDataJson).
Detail: news/intro/section text and map JSON are stored raw and emitted
with @Html.Raw without server-side sanitisation; the rich-text editor
accepts pasted HTML. Public submissions (GopY, NguoiTro) are escaped
today, so risk is admin-authored content only. A CMS author with only
TinTuc/TrangChu permission can plant script served to all visitors.
Fix: sanitize HTML server-side on save; JSON-escape MapDataJson.
##
MEDIUM - No rate limiting / no lockout (login, OTP, reset)
File: AuthController.Login, XacNhanOtp, DatLaiMatKhau; public GopY and
CongThongTinAnSXH submit endpoints.
Detail: no attempt counter/lockout on login or the 6-digit OTP; OTP is
6 decimals (Random.Next(100000,999999)) ~900k candidates, 2-min life,
unbounded online brute force. Public forms throttle 30s but per-session.
Fix: per-account/per-IP throttle + lock; OTP attempt counter that
invalidates after N failures.
##
MEDIUM - OTP & password-reset design
File: AuthController (QuenMatKhau, XacNhanOtp, DatLaiMatKhau),
Models/MaXacThuc.cs.
Detail: OTP stored plaintext in DB; a verified (DaSuDung=true) OTP is
still usable to set a new password for up to 5 min past expiry (replay
window); reset reached via GET with email+otp in URL (leak via
logs/referrer); no reset attempt limit.
Fix: one-time-use token invalidated after use/attempt, no post-expiry
grace, never place OTP in URL, bound attempts.
##
MEDIUM - Account / user-state enumeration
Detail: QuenMatKhau/DatLaiMatKhau distinguish known/unknown email;
Login discloses locked/disabled account; reset flow differences.
Fix: single generic message, server-side throttle on all states.
##
MEDIUM - Session cookie & fixation hardening
File: Program.cs (session options), AuthController.Login.
Detail: session cookie = HttpOnly true, IsEssential true, but NO
Secure and NO SameSite set; login does NOT regenerate session id
(no rotation on privilege change -> fixation risk).
Fix: cookie HttpOnly+Secure+SameSite=Lax; new session id at login and
after permission change; clear on logout.
##
MEDIUM - Missing security headers (CSP etc.)
Detail: only HSTS (non-dev) and HTTPS redirect are set. No CSP,
X-Content-Type-Options, X-Frame-Options, Referrer-Policy,
Permissions-Policy -> clickjacking/MIME-sniffing/inline-script risk.
Fix: add CSP (default-src self), nosniff, frame-options, referrer-policy.
##
MEDIUM - TLS / DB connection hardening (TrustServerCertificate)
File: appsettings.json, appsettings.Development.json, DataMTTQContext.
Detail: connection has Encrypt=True; TrustServerCertificate=True
(and Trusted_Connection / Integrated Security). TrustServerCertificate
disables cert validation -> DB transport not authenticated against MITM.
Fix: remove TrustServerCertificate; use CA-trusted SQL cert; keep Encrypt.
##
MEDIUM - File-upload content validation too permissive
File: AdminBanner, AdminTrangChhu, AdminNews (size only),
AdminDoanThe (logo), AdminQuyBienDao/QuyCuuTro (QR), AdminVanBanTaiLieu.
Detail: several uploads check only size / use original extension with
no MIME/magic allow-list; lands in wwwroot/uploads (statically served).
An admin can store arbitrary HTML/image payload served from the domain.
Fix: server-side ext+MIME+magic allow-list; store outside static root
or Content-Disposition; clamp document byte[] size.
##
MEDIUM - Mass assignment / entity binding
Detail: many CMS Create/Edit bind the EF model directly from request
(DTOs exist but inconsistent). Example AdminNews Create honours client
TrangThai -> auto-publish. Not password-overwrite but inconsistent.
Fix: bind create/edit DTOs; set status/timestamp server-side.

9. AUTHENTICATION
--------------------------------------------------------------------
- Password hashing: GOOD. PBKDF2-HMAC-SHA256, 100000 iterations, per-user
  random salt, constant-time compare (PasswordHelper.cs). Legacy 10k
  hashes are re-hashed on login (NeedsRehash). No plaintext compare.
- Login: custom session-based. Confirmed no plaintext fallback, no
  password logged, no password returned via API, not placed in URL/local
  storage. Uses ModelState.IsValid.
- Gaps: no account lockout / rate limit (MEDIUM, see #25); login POST
  lacks anti-forgery token (LOW-MED); no session-id rotation on login
  (MEDIUM, see #19); account-locked/disabled state disclosed (MEDIUM).
- Data at rest: the SMTP password, not the user password, is stored
  plaintext (HIGH #2). User password hashes are properly PBKDF2.

10. AUTHORIZATION / ACCESS CONTROL
--------------------------------------------------------------------
- [KiemTraQuy] attribute + BaseAdminController login gate; module/action
  permission model; role-version revalidation each request.
- User-management module (AdminNguoiDungController) is carefully
  guarded: Create/Edit/Delete check CoQuyenThem/Sua/Xoa and enforce

- GAP (HIGH): AdminGioiThieuController and AdminDoanTheToChucController

10. CSRF
--------------------------------------------------------------------
- Project uses the opt-in ValidateAntiForgeryToken attribute; many
  Create/Edit forms have it (good), but several state-changing POST
  endpoints (Delete / Toggle / UpdateSort) omit it (MEDIUM #6) and the
  login POST omits it (LOW). The framework default must be verified
  globally; for the code, the token is not consistently applied.
- The most sensitive user/admin management actions (DangKyAdmin, Edit,
  Delete user) DO carry the token.
- Recommend making CSRF coverage systematic (all mutating actions).

11. SQL INJECTION

- NOT FOUND. All data access uses EF Core LINQ / parameterized helpers

12. XSS
--------------------------------------------------------------------
- The rendering engine HTML-escapes @Model/View output by default; public
  user input (GopY, NguoiDanCanTroGiup) is stored and then escaped.
- The ONLY raw sinks are @Html.Raw over admin-authored content
  (News.NoiDung, section NoiDung, map JSON) with no server-side

  pasted HTML (news-editor.js).

  object values.
- JS innerHTML uses in news-editor/admin-danhsach/mttq are for static
  strings (not user-controlled on the public page); lower risk.

13. FILE UPLOAD
--------------------------------------------------------------------
- GopY upload (public): good intended design - extension + MIME +

  extension/type validation is the weak part today.

26. PASSWORD RESET
--------------------------------------------------------------------
- Token (OTP) generation: Random, not cryptographically strong order;
  2-min life not strictly enforced (grace). Marked DaSuDung on use.
- No token invalidation on failed attempts; user enumeration present.
- Recommendation: single-use, cryptographically random, time-limited,
  attempt-limited token; no URL embedding; uniform messages.

SECURITY HARDENING PHASE 3 - OTP & PASSWORD RESET
====================================================================
====================================================================

Scope   : OTP generation/storage/verification, Forgot Password,
          Password Reset, and the rate-limiting / brute-force protection
          that is directly tied to OTP and password reset.
          NOT touched: XSS, upload, session cookie, security headers,
          TrustServerCertificate, general authorization / CSRF, SMTP,
          PasswordHelper/PBKDF2, database schema, UI redesign.

Flow traced (AuthController):
  QuenMatKhau (POST, anti-forgery) -> validate email -> (optional account
  check) -> issue OTP (2 min) -> send email -> redirect XacNhanOtp?email=
  -> XacNhanOtp (POST) marks OTP used -> redirect DatLaiMatKhau ->
  PasswordHelper.HashPassword -> Login.
  Persisted in MaXacThuc table (IDMaXacThuc, Email, MaOtp, NgayTao,
  HanHet, DaSuDung, DiaChiIp).

1. OTP GENERATION (before/after)
---------------------------------
  BEFORE: System.Random (weak PRNG, predictable seed), Random.Next(100000,
  999999) - not cryptographically secure.
  AFTER : RandomNumberGenerator.GetInt32(100000, 1000000) - native
  ASP.NET/.NET CSPRNG. 6-digit numeric kept (backward-compatible, no UX
  change). No user-id/email/timestamp-derived code. ~900k candidate space
  preserved and now unpredictable.

2. OTP STORAGE (before/after)
  BEFORE: 6-digit OTP stored plaintext in MaXacThuc.MaOtp (varchar(10)).
  AFTER : Still stored in the same schema. Hashing-at-rest was evaluated
  but would require a longer hash column / a migration -> explicitly NOT
  done in this phase (no schema change rule). Compensating controls added:
  short expiry (2 min), single-active OTP, 5-attempt lockout and per-email
  /per-IP request rate caps, immediate invalidation on verify/reset. The
  DB-dump/offline brute-force scenario is mitigated by the above online
  protections.

3. OTP EXPIRATION
  HanHet remains 2 minutes. Verified and expired OTPs are rejected. Used
  OTP (DaSuDung=true) is rejected. A new issue invalidates the old active
  OTP(s) for the same email (single-active). Replay prevented at both the
  verify and reset steps.

4. ATTEMPT LIMIT (new)
  Max 5 failed guesses per OTP-window (2 min, in-memory). Reaching the
  limit invalidates all active OTPs for that email and clears the counter;
  the user must request a fresh OTP. A single wrong entry does NOT lock the
  account - only the OTP/recovery attempt is affected. No account lockout
  introduced.

5. RATE LIMITING OTP REQUEST (new)
  In-memory fixed window (single-instance; documented limitation):
   - 10 send-OTP requests / email / hour
   - 20 send-OTP requests / IP / hour
  Applies to the Forgot Password submit (the only OTP-issuing endpoint).
  No Redis / distributed limiter; counters reset on process restart.

6. RESEND PROTECTION
  The only resend path is the Forgot Password form (no separate resend
  POST). Re-requesting is throttled by the same per-email/per-IP caps;
  while an active OTP has >90s left no new one is issued; when a new OTP
  is issued the old active OTP(s) are invalidated (single-active) and the
  attempt counter is reset. No email spam allowed.

7. OTP REPLAY PROTECTION
  Verified OTP is marked DaSuDung=true and won't match again. The
  password-reset step now requires a server-side session authorization
  bound to the verified email, instead of re-passing the raw OTP in the
  URL. A used (or absent) reset authorization cannot be replayed.

8. PASSWORD RESET AUTHORIZATION
  BEFORE: after OTP verification the app redirected to
  DatLaiMatKhau?email=<e>&otp=<raw-otp> and the reset step re-validated
  that OTP with a 5-minute post-expiry "grace" (a replay window) - the OTP
  leaked into the URL and a hidden form value.
  AFTER : OTP verification stores a server-side session authorization
  (ResetPasswordEmail + ResetPasswordIssuedAt). The email used for reset
  is bound to the verified session email; a client-supplied different
  email is rejected (cross-account reset prevented). Reset is allowed only
  within ResetWindowSeconds = 300s after verification (no open-ended
  5-min grace). The raw OTP never appears in the URL, query string,
  hidden field of the reset form, logs, or responses.

9. USER ENUMERATION (hardened without breaking the forgot-password UX)
  BEFORE: The forgot-password response disclosed whether the email existed
  ("Email này không tồn tại" vs "Email tồn tại..."), letting an attacker
  enumerate valid accounts.
  AFTER : the response is identical whether or not the account exists
  (generic "Nếu tài khoản tồn tại, mã xác thực sẽ được gửi đến email của
  bạn") and redirects to the same OTP page. No email-existence, user-id,
  account-status or failure-reason is exposed. The account lookup is
  silent; the per-IP rate cap still bounds probing of arbitrary addresses.

10. TOKEN/URL EXPOSURE
  Before: the raw OTP appeared in the query string
  (/Auth/DatLaiMatKhau?otp=...) and in the reset form as a hidden input.
  After : the reset authorization is held server-side in session only; the
  OTP is entered only on the OTP page and submitted in a POST body. No OTP
  or reset credential appears in a GET URL / query string. Routes kept
  unchanged (no breaking change).

11. LOGGING / SECURITY EXPOSURE
  OTP, password, reset credential and SMTP password are never logged and
  are never rendered back into any response/browser payload. Email service
  logs only recipient addresses and generic send-results (unchanged). No
  secrets are disclosed in this report.

12. BACKWARD COMPATIBILITY
  - OTP length (6) and expiry (2 min) unchanged.
  - Existing MaXacThuc table, columns and indexes unchanged; no migration.
  - Existing OTP rows are read through the same column; no new shadow/hash
    column introduced (see 2).
  - Any legacy OTP still in the table is only valid for the rest of its
    2-min lifetime; the reset step no longer trusts a raw OTP passed in
    the URL and now requires the session authorization, so a legacy URL
    that carried ?otp= no longer completes (this is the security fix and
    cannot be achieved without it).
13. DATABASE IMPACT

15. OTP TESTS (static + traced code path)

  - Wrong OTP -> FAIL.
